# 蜀山三日 · 养成纵切 v1 规划

日期：2026-10-08。规划基线为 GitHub `main` 当前固定画景体系：听雨廊主养成、后山独立修炼场景、山门庭院独立场景、已完成的时辰／天气与环境生趣模块，以及《两盏茶》完整支线源码。

本文件只记录下一阶段开发路线与验收边界；**不代表六个切片已实施，也不自动授权提交／推送／合并／部署。** 每个切片继续遵守 Codex 做可玩结果 → 用户试玩拍板 → 修订／归档的现有流程。

## 大目标

把当前“多个完成度较高的固定场景／demo”第一次组织成一段连续的《武林群侠传》式养成体验。

目标试玩长度约 10–15 分钟，覆盖三天游戏时间。玩家需要在有限时间中做真正有机会成本的选择，并能看到自己的成长路线和世界回应。

完成时希望回答五个问题：

1. 玩家是否真的在做取舍，而不是轮流点不同按钮？
2. 去一个地方是否意味着放弃另一种确定成长？
3. 三天结束时，不同选择能否得到不同的江砚秋？
4. 世界是否会根据玩家选择产生人物／事件回应？
5. 听雨廊、后山、山门庭院是否已经像同一个游戏，而不是三个独立 demo？

## 总体范围

本纵切优先复用现有场景、美术、EnvironmentPresenter、AmbientLifePresenter 与 DemoState。工作重点从“继续增加场景技术”转向“把场景组织成游戏循环”。

计划总工作量约 **10–14 小时 Agent 实施时间**，拆成六个可独立试玩、独立回滚、独立 PR 的小 milestone。时间估算仅用于安排，不作为交付承诺。

明确暂缓：

- `addons/shu_scene_runtime/` extraction；
- 存档；
- 完整月历；
- 完整关系系统；
- 金钱／装备／技能树；
- 战斗；
- 大量新属性；
- 新天气种类、季节和随机气候模型；
- 重构《两盏茶》；
- 继续堆复杂实时光照；
- 同一切片同时做基础设施重构和新玩法。

## M1 · 多场景养成骨架

**预计：1.5–2.5h**

### 玩家结果

从听雨廊进入后山，再返回听雨廊；往返前后的养成状态完全连续。

最小流程：

```text
听雨廊
  ↓
进入后山
  ↓
后山固定场景
  ↓
返回
  ↓
听雨廊
```

### 实现边界

- `DemoState` 继续是唯一 gameplay authority。
- 允许增加很薄的 scene routing / return-context 层，只负责场景进入、返回与当前场景身份。
- 后山独立 demo 的 QA 控件继续保留在 demo，不直接搬进正式流程。
- 不新增剑术，不新增行动结算，不新增剧情。

### 核心验收

例如进入前：

```text
第1日 · 巳时
精力 78
修为 12
```

从后山返回后必须仍是同一状态。

**试玩问题：**跨场景往返是否已经像同一个游戏，而不是打开另一个 demo？

## M2 · 后山练剑

**预计：1.5–2h**

### 玩家结果

增加一个真正的新养成选择：

```text
后山练剑
→ 进入后山
→ 简短练剑表现
→ 剑术增长 / 精力消耗 / 时间推进
→ 返回养成
```

### 最小状态扩展

只新增一个核心成长值：

```text
swordsmanship
```

数值是 demo 参数，由统一规则／宿主结算持有，不在 scene adapter 中复制。

### 设计目标

第一次形成明确的：

```text
吐纳 → 修为
练剑 → 剑术
```

玩家使用同一段有限时间，不能同时最大化两条成长。

### 核心验收

**试玩问题：**玩家是否开始觉得“这一回合练吐纳还是练剑”是一个有意义的选择？

---

## M3 · 山门闲逛

**预计：1–1.5h**

### 玩家结果

增加：

```text
闲逛山门
```

进入已验收的山门庭院，消耗游戏时间，但默认不保证修为／剑术等确定数值收益。

### 设计目标

建立最关键的机会成本之一：

```text
确定成长：练功
vs
未知可能：闲逛
```

第一版允许一次闲逛“什么特殊事件都没有发生”。庭院本身的环境、猫与生活感仍应使这次选择不是空白页面。

### 核心验收

**试玩问题：**明知没有确定数值收益，玩家是否仍愿意偶尔花时间去山门看看？

---

## M4 · 余观涛首次偶遇

**预计：1.5–2h**

### 玩家结果

首次让养成／地点选择触发一个短人物事件。

候选触发条件保持极简，例如：

```text
Day >= 2
AND
首次满足条件的山门闲逛
```

或使用一个已经真实存在的成长条件。实施时只选一种，不提前建立复杂事件系统。

### 事件范围

- 余观涛首次真正进入可玩世界；
- 原创短对白；
- 约 4–8 句；
- 30–90 秒；
- 最多一个选择；
- 不要求数值奖励；
- 不展开完整师叔路线、善恶路线或主线谜团。

### 设计目标

形成：

```text
养成选择
→ 去了某个地点
→ 遇见某个人
→ 这次游戏经历与另一条路线不同
```

### 核心验收

**试玩问题：**玩家是否第一次感到“世界会回应我的安排”，而不是所有内容都在菜单里等我点？

---

## M5 · 三日养成循环

**预计：2–2.5h**

### 玩家结果

建立明确的试玩时间盒：

```text
Day 1
Day 2
Day 3
→ 三日小结
```

每天结束有短 summary，不做评分等级。

示例：

```text
第一日

吐纳 × 2
练剑 × 1
闲逛 × 1

修为 +24
剑术 +10

山门所遇：无
```

另一条路线可以自然得到不同结果。

### 状态

允许增加最小的：

- daily action history；
- seen events；
- 每日／三日汇总所需统计。

不要因此建立通用 analytics／save schema。

### 设计目标

让玩家能回答：

> “这三天，我把江砚秋养成了什么样？”

### 核心验收

至少两条实际试玩路线在第三日结束时出现明显不同的成长分布／经历记录。

## M6 · 三日纵切整体收尾

**预计：2–3h**

不增加新系统，专门解决连续体验。

### 必验收项

#### 1. 环境连续性

例如：

```text
听雨廊 · 申时 · 小雨
→ 后山
仍是申时 · 小雨
→ 返回
仍保持一致
```

场景自己的表现参数可以不同，但游戏层时辰／天气语义必须连续。

#### 2. Ambient Life 注意力退让

修炼、对白和短事件期间，猫、鸟等不得争夺主叙事注意力；环境仍可保持低强度生命感。

#### 3. Return context

后山练剑、山门闲逛和余观涛事件结束后，都返回正确养成上下文，不 reset、不生成第二份 gameplay state。

#### 4. 完整连续试玩

真实走通：

```text
新开始
→ 三天
→ 多种行动
→ 至少一次地点往返
→ 至少一次山门事件
→ 三日小结
```

优先验证 Web；平台证据与实际执行分开记录。

### 最终验收

连续试玩约 10–15 分钟后，由用户判断：

- 是否存在真正的养成取舍；
- 时间是否具有机会成本；
- 成长路线是否开始分化；
- 世界是否产生回应；
- 三个场景是否已经组成统一游戏体验。

## 跨切片工程原则

### 唯一 Gameplay Authority

时间、精力、修为、剑术、事件状态统一由宿主持有。Environment、Ambient Life、场景 adapter 只能观察，不得自己结算。

### 场景不是第二套游戏

后山和庭院现有 standalone demos 继续作为研发／视觉 QA harness；正式养成流程只复用其场景能力，不直接暴露 demo 的时间／天气预览面板。

### 先验证玩法，再抽 runtime

当前 Environment／Ambient modules 已有真实复用证据，但本大 milestone 的优先级是游戏循环，不在中途创建 `shu_scene_runtime` addon。若三日纵切成立，runtime extraction 再作为独立纯重构里程碑评估。

### 小 milestone 独立验收

建议一个小 milestone 对应一个新的 Codex chat 和一个独立 PR：

```text
M1  多场景养成骨架
M2  后山练剑
M3  山门闲逛
M4  余观涛首次偶遇
M5  三日循环
M6  纵切整合收尾
```

任何一步若试玩结果不成立，先在该层修正，不因为后续规划已经存在而继续堆系统。

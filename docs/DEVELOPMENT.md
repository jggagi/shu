## 每轮协作

1. **Codex 定一个小切片**：写清本轮目标、对应需求、玩家能看到的结果和验收点；将新设计标为提案。每轮优先只解决一个玩法或布局问题。
2. **Codex 实现并交付**：提供本次可玩入口、对应 commit、短试玩步骤、已验证结果和已知问题。布局与玩法数据分开，便于 Codex 根据试玩反馈调整排版。
3. **用户试玩拍板**：通过截图标注、文字反馈或参考图说明希望怎样改变、哪些部分保留，并对玩法、布局和方向拍板。
4. **Codex 修订**：先检查现有修改，保留用户内容；按反馈调整玩法与排版，复查受影响流程。用户认可的结果才记录为确认。
5. **Codex 复盘与计划**：更新本文件的当前切片状态与下一个验收点；新产品决定写入决定日志并同步规格。用户仍在调整的部分不作为扩大内容量的依据。

普通、已授权的切片修订持续推进，不重复索要确认。引擎迁移、核心玩法或角色方向变更先给具体方案；购买素材、公开发布或其他超出当次任务的操作需有相应授权。

## D01：问心院首课（已实现，待用户验收）

对应 R01、R03、R04、R05、R07、R08。目标是让用户在约 5 分钟内判断构图与基本养成节奏。以下为 demo 提案，不是完整玩法的定稿。

**范围**：一个原创固定背景；顾青岚与陆松风；时间、精力、修炼进度三个最小状态；「修炼」「请教师傅」「休息」三个行动；短小原创师傅对话与一个选择；结果反馈与重置。

**玩家可观察的验收点**：

- 打开 Web 入口能看见完整养成场景、状态面板与对话区，主角和师傅均在此画面内。
- 修炼推进时间、消耗精力、增加修炼进度；效果立即可见，精力不足时给出可理解的提示。
- 请教师傅在原场景开启短对话，选择后得到明确反馈并返回行动状态；操作不能重复结算。
- 休息推进时间并恢复精力；重置能回到已知初始状态，便于反复评审。
- 在 Windows 的 Edge／Chrome 中实际操作上述循环；复查窗口缩放后对话和操作区是否被遮挡，记录所用窗口尺寸。
- 从同一 Godot 工程导出 Windows 原生版本，启动并实际操作同一循环；分别记录 Web 与 Windows 的构建、启动和试玩结果。
- 用户提出一次排版调整后，Codex 能改人物位置、面板比例或字体，无需重写行动规则。

当前不实现长篇剧情、完整战斗、地图漫游、多人、账号服务或 Steam 集成；这是分阶段安排，后续是否需要以产品讨论为准。

**最小复用边界**：场景展示／布局参数、人物与对话资料、状态与行动结算分开。只有第二个用例实际出现时才抽取共用模块；数值先用小型数据表，不建内容编辑器。

## 已确认技术方案

2026-10-04：用户确认 **Godot 4 稳定版 + GDScript**，选择时考虑后续 Steam。D01 已锁定 Godot 4.7.2 stable 与匹配导出模板，工程沿用该方案。

- D01 已使用 Compatibility 渲染模式与单线程 Web 导出，并检查浏览器加载与窗口适配；加入音效后再验证音频兼容。[Godot Web 导出说明](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- 固定背景、Q 版人物、状态面板与对话统一使用 Godot 场景和控件；玩法、人物／对话数据与布局分开维护。
- 同一工程分别生成 Web 试玩版与 Windows 原生版，持续检验两端核心流程；[Windows 导出说明](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)。
- 后续存档数据采用明确版本，分别验证浏览器持久化和桌面文件读写；不能将一端成功当作另一端已验证。
- Steam 成就、云存档等在桌面阶段按需接入，平台功能与核心玩法分开；首个 demo 保持短小范围。

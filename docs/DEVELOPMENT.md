## 每轮协作

1. **Codex 定一个小切片**：写清本轮目标、对应需求、玩家能看到的结果和验收点；将新设计标为提案。每轮优先只解决一个玩法或布局问题。
2. **Codex 实现并交付**：提供本次可玩入口、对应 commit、短试玩步骤、已验证结果和已知问题。布局与玩法数据分开，便于用户排版。
3. **用户试玩与排版**：可直接调整布局文件，也可给截图标注、文字反馈或参考图；重点描述希望怎样改变、哪些部分保留。
4. **Codex 修订**：先检查用户修改，保留其排版；按反馈做最小改动，复查受影响流程。用户认可的结果才记录为确认。
5. **Codex 复盘与计划**：更新本文件的当前切片状态与下一个验收点；新产品决定写入决定日志并同步规格。用户仍在调整的部分不作为扩大内容量的依据。

普通、已授权的切片修订持续推进，不重复索要确认。引擎迁移、核心玩法或角色方向变更先给具体方案；购买素材、公开发布或其他超出当次任务的操作需有相应授权。

## D01：养成场景与师傅互动（下一步，尚未实现）

对应 R01、R03、R04、R05、R07。目标是让用户在约 5 分钟内判断构图与基本养成节奏。以下为 demo 提案，不是完整玩法的定稿。

**范围**：一个原创固定背景；顾青岚与陆松风；时间、精力、修炼进度三个最小状态；「修炼」「请教师傅」「休息」三个行动；短小原创师傅对话与一个选择；结果反馈与重置。

**玩家可观察的验收点**：

- 打开 Web 入口能看见完整养成场景、状态面板与对话区，主角和师傅均在此画面内。
- 修炼推进时间、消耗精力、增加修炼进度；效果立即可见，精力不足时给出可理解的提示。
- 请教师傅在原场景开启短对话，选择后得到明确反馈并返回行动状态；操作不能重复结算。
- 休息推进时间并恢复精力；重置能回到已知初始状态，便于反复评审。
- 在 Windows 的 Edge／Chrome 中实际操作上述循环；复查窗口缩放后对话和操作区是否被遮挡，记录所用窗口尺寸。
- 用户提出一次排版调整后，Codex 能改人物位置、面板比例或字体，无需重写行动规则。

当前不实现长篇剧情、完整战斗、地图漫游、多人、账号服务或 Steam 集成；这是分阶段安排，后续是否需要以产品讨论为准。

**最小复用边界**：场景展示／布局参数、人物与对话资料、状态与行动结算分开。只有第二个用例实际出现时才抽取共用模块；数值先用小型数据表，不建内容编辑器。

## 引擎与素材建议的时机

以下为 2026-10-04 查阅官方资料后的候选与项目判断，尚未安装或选定：

| 候选 | 何时有帮助／本项目判断 |
| --- | --- |
| HTML／CSS + TypeScript | 建议先用来验证固定面板、对话和用户排版；属于首 demo 的技术提案。若足够支撑养成玩法，不必为使用引擎而迁移。 |
| [Phaser](https://github.com/phaserjs/phaser) | 官方定位为面向浏览器的 2D 游戏框架，支持 Canvas／WebGL。需要人物动画、场景调度或更多游戏式交互时再比较，届时锁定具体版本。 |
| [Godot](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html) | 需要场景编辑与桌面导出工作流时再评估。官方当前 Web 文档列出 WebAssembly／WebGL 2.0 要求，并说明 Godot 4 的 C# 项目不能导出 Web；若选择应先验证一个小型 Web 导出，不能只凭 Steam 方向决定。 |
| [Kenney 素材目录](https://kenney.nl/assets) | 有 UI、2D 与音频分类，可在占位按钮／提示音需要时筛选；是否符合宋式审美要逐项评审，不能替代已确认的美术方向。 |
| [OpenGameArt](https://opengameart.org/content/faq) | 需要基础音效或其他占位素材时查找。官方 FAQ 要求遵循每份素材的许可与署名条件，不能把整站当作统一授权。 |

正式 Q 版人物和中国画背景应等 D01 排版反馈稳定后，再建议原创绘制或生成的分层素材方案。现在不批量下载、购买或创建正式美术。

素材一旦导入，放入项目 assets/ 或 vendor/，同时记录来源、作者、版本、许可／署名要求、改动与 SHA256；需要的素材随项目管理或有可复现获取步骤。运行不能依赖本机素材库的绝对路径。验证截图、日志、缓存放被忽略的 .local/；版本化发布产物与开发材料分开。
